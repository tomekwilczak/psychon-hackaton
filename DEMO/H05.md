Rozstrzygnięcie: pakiet dopisuje **wyłącznie** własny wpis
(`{ label: "Kursy", href: "/panel/kursy", order: 20 }`) i nie dotyka wpisów innych pakietów.

**Skutek:** Session 2 (faza 2, front) dopisuje wpis do rejestru; menu nie wymaga osobnego
PR-a sztabu.

### 2026-08-28 — faza 4 (do rozstrzygnięcia przez strażnika kontraktu)

Trzy pozostałe odstępstwa pakietu. Numeracja (1)–(5) obejmuje także dwie decyzje bramy
otwierającej powyżej: **(2)** = wpis w `public_routes.php`, **(4)** = wpis w rejestrze menu.

**(1) Zdjęcie sekwencyjnej blokady dla ról nieuczestniczących — DO ZATWIERDZENIA**

`CourseAccess::state()` napisano dla osób uczących się: prowadzący i administracja nie mają
wierszy `lesson_progress`, więc funkcja zaraportowałaby im etapy 2–10 jako `locked` — kłódki
na treściach, którymi sami zarządzają. Matryca ról (`docs/system/03-role-i-uprawnienia.md`
§2, wiersz „Kursy: przeglądanie i nauka") daje `project_manager` i `super_admin` pełne ✔,
więc kłódka jest tam po prostu błędem.

Rozstrzygnięcie pakietu: dla ról spoza `volunteer` / `student` blokada nie obowiązuje —
status `locked` jest przed serializacją sprowadzany do `in_progress`
(`backend/app/Http/Resources/CourseListResource.php`, `CourseController::show()` w ogóle nie
sprawdza stanu). Wartość zostaje wewnątrz słownika `course.status` (kontrakt §3.4), więc
kontrakt HTTP się nie zmienia. Reguła nie jest zapisana w żadnym dokumencie źródłowym —
stąd zgłoszenie.

**(3) Odstępstwo od kryterium odbioru H05.3 wraz z obejściem — DO ZATWIERDZENIA**

Kryterium H05.3 brzmi: *„Zaliczenie testu kursu 2 (helper `demo:pass-test` ze startera) →
kurs 3 przechodzi na `in_progress`"*. **Nie jest prawdziwe.** `demo:pass-test`
(`backend/app/Console/Commands/DemoPassTest.php:79`) tworzy wyłącznie zdane podejście
`TestAttempt`; `CourseAccess::state()` wymaga od poprzedniego etapu **kompletu ukończonych
lekcji ORAZ** zdanego testu (`backend/app/Support/CourseAccess.php:36-42`), a marta ma
2 z 5 lekcji kursu 2 (`DemoSeeder.php:350`). Po samym `demo:pass-test` `missing` = `["lessons"]`
i kurs 3 zostaje `locked`.

Ukończenie lekcji to `POST /lessons/{id}/complete`, czyli pakiet **H06**. Żeby H05 dało się
odebrać niezależnie, pakiet dokłada własną komendę konsolową
`demo:complete-lessons {email} {courseSlug}`
(`backend/app/Console/Commands/DemoCompleteLessons.php` — nowy plik, zero konfliktu na
plikach współdzielonych), zapisującą wiersze `lesson_progress` w tym samym kształcie co
`DemoSeeder::completeLessons()` (`watched_seconds = duration_seconds`, `active_seconds ≈ 85 %`,
`is_completed = true`), idempotentnie per lekcja. Ścieżka demo to więc **dwie** komendy
zamiast jednej — patrz „Przejście demo" niżej.

Prośba do strażnika: przeredagowanie kryterium H05.3 w `01-pakiety-zadan.md` na dwie komendy
albo potwierdzenie, że komenda H05 jest akceptowalnym obejściem do czasu wejścia H06.

**(5) Zawężenie `S (prowadzone + podgląd)` do samych kursów prowadzonych — DO ZATWIERDZENIA**

Matryca ról daje prowadzącemu `S (prowadzone + podgląd)`. Część „prowadzone" ma nośnik
w danych (`course_assignments` z `unassigned_at IS NULL`) i została zaimplementowana
(`backend/app/Queries/CourseCatalogQuery.php`). Część **„podgląd" nie ma żadnego nośnika** —
nie istnieje kolumna, flaga ani tabela mówiąca, które *nieprowadzone* kursy prowadzący może
podejrzeć. Pakiet ją pominął: `joanna@demo.pl` widzi dokładnie kursy 1–3.

Prośba do strażnika: rozstrzygnięcie, czy „podgląd" oznacza (a) wszystkie opublikowane kursy
tylko do odczytu, (b) nic więcej niż prowadzone (stan obecny), czy (c) osobną, przyszłą
funkcję. Zgłaszane razem ze znanym ograniczeniem danych demo niżej.

## Przejście demo

> Wersja fazy 4 (automaty). Bramka zamykająca HC1 dopisuje wynik przejścia na stagingu.

Wszystkie komendy backendu idą przez docker (`php`/`composer` nie istnieją na hoście).
Konta i hasła: `docs/hackathon/04-seed-demo.md` §2 — hasła `demo1234`, administracyjne
`admin1234`.

**0. Czysty stan**

```bash
docker compose down -v && bash scripts/setup.sh   # Windows: scripts\setup.ps1
cd frontend && npm run dev                        # front :3000, API :8000, Mailpit :8025
```

**1. Katalog uczestniczki (kryteria 1 i 2)**

Zaloguj się jako `marta@demo.pl` / `demo1234`, otwórz **Kursy** (`#/panel/kursy`).
Oczekiwane, wprost z `04-seed-demo.md` §3: etap 1 „Ukończony" / 100 %, etap 2 „W toku" / 40 %,
etapy 3–10 „Zablokowany" / 0 %.

**2. Egzekwowanie po stronie serwera (kryterium 4)**

Wpisz ręcznie w pasek adresu `/panel/kursy/interwencja-kryzysowa`. Ekran blokady nazywa
etap 2 i wymienia oba brakujące warunki. Pod spodem:

```bash
curl -H "Authorization: Bearer <token marty>" http://localhost:8000/api/v1/courses/interwencja-kryzysowa
# → 403 { "error": { "code": "course_locked", "reason": { "required_course_id": 2, "missing": ["lessons","test"] } } }
```

**3. Odblokowanie etapu i dzwonek (kryterium 3)**

```bash
docker compose exec app php artisan demo:complete-lessons marta@demo.pl wywiad-psychologiczny
docker compose exec app php artisan demo:pass-test        marta@demo.pl wywiad-psychologiczny
```

Przeładuj **Kursy**: etap 2 → „Ukończony" / 100 %, etap 3 → „W toku" i jest klikalny.
W dzwonku H16 pojawia się `course.unlocked` z linkiem `/panel/kursy/interwencja-kryzysowa`
(UI dzwonka może być jeszcze zaślepką startera — wtedy pokaż wiersz w `notifications`
i jego symulowany e-mail w Mailpicie / `GET /admin/emails`).

**4. Brak duplikatów ogłoszeń**

Przeładuj katalog jeszcze dwa razy — liczba powiadomień `course.unlocked` nie rośnie.
Pokrycie automatyczne: `CourseUnlockNotificationTest`.

**5. Materiały (podpisany, wygasający link)**

Na stronie kursu 2 kliknij materiał — pobiera się PDF. Skopiowany link po 15 minutach jest
odrzucany, tak samo link z ręcznie podmienionym parametrem `u`.
Pokrycie automatyczne: `MaterialDownloadTest`.

**6. Pozostałe role**

- `filip@demo.pl` (student) — widzi wyłącznie webinar poza sekwencją i może go otworzyć.
- `joanna@demo.pl` (prowadząca) — widzi dokładnie kursy 1–3 (jej przypisania).
- `admin@demo.pl` / `admin1234` — widzi wszystkie kursy i **żadnej** kłódki (odstępstwo 1).

**7. Wyłącznik pakietu**

`config/features.php` → `'h05' => false` usuwa trasy i wpis w menu bez błędów.

**Bramki automatyczne (zielone na 2026-08-28)**

cd frontend && npm run lint && npm run build

## Znane ograniczenia danych demo

**Konto `filip@demo.pl` ma postęp w kursie, którego nie widzi**

Seed daje `filip@demo.pl` (rola `student`) pięć ukończonych lekcji kursu 1
(`backend/database/seeders/DemoSeeder.php:381`, „konto przeklikane" — rzetelność ≈15 %).
Jednocześnie matryca ról daje studentowi `✔ (zaproszone)`, czyli wyłącznie kursy spoza
sekwencji (`sequence_order IS NULL`). Kurs 1 jest etapem ścieżki, więc filip **nie zobaczy
go w katalogu** i dostanie **404** przy `GET /courses/podstawy-pomocy`.

Funkcjonalnie nic się nie psuje — H07 (rzetelność) czyta `lesson_progress` bezpośrednio,
a demo flagi rzetelności działa. Niespójna jest **narracja**: konto „przeklikane" nie ma
dostępu do tego, co przeklikało, więc nie da się tego pokazać z perspektywy samego filipa.

Do zgłoszenia strażnikowi schematu razem z odstępstwem (5). Możliwe wyjścia (decyzja poza
tym pakietem, wymaga zmiany seeda, nie kodu H05):

- przenieść postęp filipa na webinar spoza sekwencji, albo
- dodać filipowi drugą rolę / zaproszenie do kursu 1, gdy H08b dowiezie zaproszenia, albo
- zostawić jak jest i pokazywać rzetelność filipa wyłącznie z panelu administracji.
